## Коротко

- **Codex сделал быстрее и шире.** Он уложился примерно в 2 ч 08 мин активной работы, сверстал все семь вариантов главной из Figma, включая два дополнительных десктопных (1500 px в тёмной теме и 1296 px с красным акцентом), и собрал каталог из 312 образцов. Визуальную сверку он провёл тщательнее: с парными снимками «Figma — браузер».
- **Но архитектура у него не годится для живого сайта.** Страница целиком собирается в браузере на JavaScript из JSON с координатами узлов Figma. В HTML нет ни одного товара, раскладка держится на фиксированных профилях с пикселями из макета, табы не переключают содержимое, а тёмная тема меняет ещё и ширину контента. На вопрос о причинах Codex сам назвал это «архитектурной ошибкой» (см. раздел «Что ответил Codex»).
- **Мой вариант медленнее и дороже по ресурсам, зато это рабочая вёрстка.** Он занял около 2 ч 50 мин активной работы и примерно в 4 раза больше токенов. Результат — статический HTML из партиалов, резиновый адаптив, прогрессивное улучшение на JS, адаптивные картинки. Его можно отдавать бэкенду, например натягивать на шаблоны 1С-Битрикс.
- **Итоговая оценка** (подробно — в разделе «Оценка по критериям»): Claude Code — **8,5 из 10**, Codex — **6 из 10**.

## Что ответил Codex

Я задал Codex шесть вопросов в копии его чата этапа 3. Копия сделана командой `codex exec fork` в режиме только чтения, так что исходный чат и проект не изменились. Суть его ответов:

1. **Почему страница собирается на JS.** Он переиспользовал JS-компоненты каталога, которые строят разметку из данных Figma. Без JS товары и тексты не появляются, а для 1С-Битрикс разметку придётся собирать заново в PHP-шаблонах. Его собственная оценка: «Для витрины это была моя архитектурная ошибка».
2. **Почему фиксированные профили.** Так было быстрее воспроизвести контрольные экраны. Он признал, что разумнее было сделать один DOM с резиновой сеткой, а размеры из Figma использовать только для проверки.
3. **Почему тема меняет ширину.** В Figma было три десктопных сочетания «цвет + контейнер», и он связал их в коде. Признал, что тему и ширину стоило сделать независимыми.
4. **Почему у картинок нет `srcset` и размеров.** Экспортировал по одному WebP на исходник; хеши в именах помогали сверять файлы с Figma. Подготовку `srcset` и размеров, по его словам, пропустил.
5. **Почему дизайн-система — это каталог.** Каталог решал задачу приёмки. Ошибкой он считает то, что рабочая главная зависит от данных демонстрационного каталога.
6. **Что переделал бы первым.** Серверные HTML-шаблоны на одной карточке и секции, адаптивную сетку на CSS, JS только для взаимодействий, проверку без JS и в Битрикс. Затем — разделить тему и ширину и сделать `srcset`.

## Почему результат Codex вызывает недовольство — по фактам

- Страница выглядит похожей на макет, но это **муляж макета, а не вёрстка**: правка любого текста или карточки требует правки JSON с координатами, а натянуть такую страницу на CMS нельзя.
- **Без JavaScript страница пустая.** Это риск для индексации и для пользователей с медленным или сломанным JS.
- **Поведение демонстрационное:** табы не переключают содержимое, «тёмная тема» на самом деле переключает другой вариант макета (тёмный фон, красный акцент, контент 1500 px) и не запоминается.
- **Адаптив хрупкий:** на ширинах между профилями появляются дефекты (на 1100 px — прокрутка вбок и развалившаяся шапка), хотя в его отчёте указано, что проверено 22 промежуточные ширины.
- **Картинки тяжёлые:** нет `srcset` и размеров, а имена файлов — хеши.

## Слабые места моей работы

- Не сверстал десктопные варианты 1500 / 1296 из Figma — ограничился основным фреймом 1920.
- Дизайн-система покрывает только компоненты главной: фильтры, цена, сертификат и вакансии отложены, хотя вы и согласились на это.
- HTML тяжёлый (477 КБ): у трёх секций с табами по четыре копии панелей. На реальном сайте панели лучше подгружать по запросу или отдавать с бэкенда.
- Сверка с макетом шла по геометрии и выборочным снимкам, без парных полноразмерных снимков, как у Codex.
- Ушло больше времени и токенов. Отчасти это цена работы мелкими шагами с остановками на проверку, отчасти — два сжатия контекста.
- Контраст серых текстов и лейблов ниже WCAG AA — оставлен как в макете по вашему решению.
